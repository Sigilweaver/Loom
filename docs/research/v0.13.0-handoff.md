# v0.13.0 release handoff

This branch completes the cloud-work closeout described below. Release publication, deployment and native installer verification remain manual. Keep this document as a record of verified behavior and the limits that remain after v0.13.0.

## Verified behavior

- Hub-triggered executions use capability tokens for the triggering user or schedule creator. There is no shared-secret fallback. Automatic Server selection chooses the least-loaded online Server, with random tie-breaking.
- Schedule dispatch polls persisted occurrences using the database clock. A row lock serializes occurrence advancement and execution insertion in one transaction. Competing dispatchers create one execution; an uncommitted claim is available to another dispatcher after rollback. Standard cron weekdays (0/7 Sunday, 1 Monday), symbolic days, lists, ranges and steps are validated consistently. Schedule edits are read from PostgreSQL, and missed cron intervals are coalesced into one attempt.
- Execution records have a heartbeat and stale-run recovery. Startup and periodic sweeps mark interrupted queued/running runs failed with an unknown Server outcome. Runner and cancellation transitions lock and refresh the row, preserving terminal results. Shutdown cancels tracked runners. This is recovery bookkeeping, not resumption of the Server request.
- Audit events receive their identity and timestamp before hashing, concurrent writers are serialized, and the hash covers authorization context. Legacy rows are reported as unverifiable. Tokenless Server registration no longer overwrites another registration.
- Server expression evaluation uses an allowlist; restricted file paths are enforced during execution and SQLite URI access. Preview All, socket preview, schema inspection and profiling skip Output writers. Run still writes outputs. Invalid tool configuration, invalid graphs and empty workflows return HTTP 400. Automatically generated session tokens are no longer logged.
- Studio has advisory Validate/Problems UI, version-aware Hub workflows, corrected serialized Input/Output/Sample validation fields, and accurate Unique/Unpivot blocking flags. Desktop file IPC is limited to dialog-granted paths. Studio logs a generic credential-resolution failure without including the raw native exception; this does not establish native-boundary credential isolation.
- Release builds create a draft. Publication triggers R2 mirroring and Docker builds. Pre-releases do not update the stable download index or Docker `latest`. The release guide already describes this flow.

## Validation

The full local gate covers repository release scripts, Server lint/types/tests, Studio lint/types/tests, Hub backend lint/types/PostgreSQL tests, Hub frontend lint/types/tests, the docs production build and live Studio/Server integration:

```bash
python scripts/test.py --full --no-coverage --strict -p
```

Both Studio Web and Hub frontend production builds also passed. The Hub Docker image built successfully; its frontend assets and migration 009 were inspected inside a container without network access. Electron signing configuration was corrected for electron-builder 26 and all three packaging configurations passed schema validation. Scheduler integration tests cover competing dispatchers, rollback/failover, persisted configuration changes, disabled schedules and legacy schedules with a future start. Native packaging and GUI checks are separate release requirements; Python and web checks do not validate an installed desktop application.

## Release steps

1. Confirm the release secrets exist: `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`, `R2_BUCKET_NAME`, `R2_ENDPOINT_URL`, and optional `R2_CDN_URL`. Check signing credentials in the release workflow.
2. Merge to `main` and obtain a passing CI run on the exact commit to tag. Docs-only commits can skip CI, so dispatch it explicitly when necessary. The release workflow checks that run.
3. Set the date on the `[v0.13.0]` changelog entry and tag `v0.13.0` on `main`. Repository version fields stay at `0.0.0-dev`; CI injects the tagged version.
4. Back up PostgreSQL and persistent workflow/artifact storage before upgrading Hub. Apply `alembic upgrade head`, including migrations 008 (audit hash version) and 009 (execution heartbeat). Edit and save existing weekly schedules to recalculate any pending occurrence generated under the older Monday-based weekday mapping.
5. Review the draft release's assets and checksums. Smoke-test the installers and bundled Server on supported platforms, then publish the draft and verify R2 mirroring and Docker image publication.

## Supported deployment and recovery limits

Run one Hub process. Transactional schedule claims prevent duplicate scheduled dispatch, but the in-memory SSE event broker does not share live events between replicas. The default token store is also in memory; `TOKEN_STORE_BACKEND=postgres` shares tokens but does not replace the event broker. A complete multi-replica topology remains roadmap work (#69 beyond schedule dispatch).

Execution records survive restart, but queued/running requests are not resumed or retried (#68 remains partial). Runners heartbeat every 15 seconds; a startup and 60-second sweep marks records failed after `EXECUTION_STALE_SECONDS` (default 120). Hub cancellation only changes bookkeeping and does not stop Server work. The Server may complete after Hub interruption or timeout. Once a scheduled execution commits, a failed run waits for the next occurrence; failures before the execution/claim commit can be retried by a later poll.

Persist both workflow and artifact storage. The provided compose files mount workflow storage but do not provide an artifact volume. Server self-registration requires explicit `HUB_SERVER_TOKEN` and `PUBLIC_ENDPOINT_URL` configuration; those are not supplied by the base compose files. Each Server needs its own token, so shared-token `--scale` advice has been removed from the Docker README. The Server `.env.example` still lists port 58000 while the documented Server port is 25811; configuration examples and compose changes need a separately reviewed deployment change.

## Roadmap and platform limits

- Cookie sessions with CSRF protection (#118), complete auditing of mutations, and encryption of stored Server registration tokens require further design and implementation.
- Renderer credential isolation (#89) is partial: Full builds use the native connection proxy, while Client builds, development mode and remote servers still resolve client-owned credentials in the renderer. Remembered Hub session tokens and AI keys also need a stronger persistence design.
- Tauri is built by a manually dispatched workflow and is not part of the tagged release (#107). The Electron-to-Tauri migration (#102), OS keyring/settings migration and native sidecar/installer smoke tests remain separate work. macOS release builds are not notarized.
- Admin Settings, SSO/OIDC, per-user automation tokens, notifications and broader UI/accessibility work remain roadmap items. Workflow artifacts and auditor execution details are currently API-only.

Historical lists of suspected dead code and already-fixed defects have been removed. The release notes and user/developer docs now describe the implemented scheduling, recovery, preview, validation and release behavior.
